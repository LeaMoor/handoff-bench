## Часть 1. Собственный оркестратор: поведение агентов, банковский результат и отчёт пользователю

### 1. Проверка меняет поведение ещё до появления ошибок

В первых прогонах Luna получила **41 правильный исход из 42 при каждом из трёх каналов**, однако принимала решения по-разному. По сохранённому показателю самостоятельной проверки истории родитель проверил счёт в 29/42 эпизодов со словами исполнителя, в 25/42 с бланком и в 39/42 с банковской выпиской. Ответ родителя unknown встретился соответственно в **17, 20 и 3** эпизодах. У Haiku родитель сам проверял в 41, 41 и 42 случаях из 42. Один балл за правильность скрывает и разную частоту проверки, и разную готовность назвать исход известным. Каждый канал здесь объединяет два банковских мира. [Пересчёт первой ночи](проверки_первый_прогон.csv)

### 2. Что даёт проверка, если списание всё равно не видно?

Собственный оркестратор, один и тот же текстовый канал, долгая задержка, без дополнительного блока правил. Три шаблона по семь сидов на модель в каждом мире. Ниже два вопроса к одним эпизодам: выполнена ли работа по состоянию банка и что родитель сказал пользователю. Ответ unknown может быть честным и после успешно проведённого платежа.

**Мир A. Первая попытка оплаты потерялась** (ячейка 24). Чтобы выполнить задачу, команде нужно всё-таки провести платёж.

|---|---:|---:|---:|---:|
| Haiku | 7/21 | 14/21 | 21/21 | 12/21 |
| DeepSeek | 21/21 | 0/21 | 21/21 | 0/21 |
| GPT-4o-mini | 21/21 | 0/21 | 7/21 | 0/21 |
| Luna | 21/21 | 0/21 | 11/21 | 2/21 |
| Qwen | 9/21 | 12/21 | 7/21 | 6/21 |
| GLM | 21/21 | 0/21 | 21/21 | 0/21 |

Haiku и DeepSeek проверяли сами во всех эпизодах, а довели до конца соответственно семь и двадцать один заказ. Наблюдение «модель проверяет банк» само по себе слабо описывает результат: важно, какое действие следует за пустой проверкой.

**Мир B. Первая оплата прошла, но ответ потерян** (ячейки 25 и 29). Здесь проверяем, помогает ли замена слов исполнителя выпиской. В каждой клетке ниже указаны количества по схеме «слова → выписка», из 21.

|---|---:|---:|---:|
| Haiku | 20 → 20 | 21 → 21 | 1 → 1 |
| DeepSeek | 20 → 12 | 21 → 21 | 1 → 8 |
| GPT-4o-mini | 2 → 0 | 7 → 12 | 17 → 17 |
| Luna | 19 → 13 | 15 → 21 | 7 → 7 |
| Qwen | 16 → 12 | 7 → 7 | 7 → 11 |

У GLM при переходе на выписку число полностью выполненных заказов упало с 15 до 6, хотя родитель проверял банк во всех случаях. При этом done стало чаще. У Luna число проверок выросло до 21, но полных оплат стало меньше. Получается практически важная развилка: дополнительный вызов проверки помогает, когда проверка может показать истину; при задержке даже добросовестная проверка может дать устаревшую картину. Конкретные траектории отдельных эпизодов восстанавливаются по журналам.

Отдельное парное сравнение 0/72 против 46/72 использует меньшую выборку миров, где прерывание произошло в обоих условиях. ## Как читать файл
A и B — номера ячеек. Сопоставление внутри модели по world, template, seed и repeat. Берутся валидные строки. Для основной сетки используется порядок scripts/grid.py: сортировка папок, затем первая валидная копия. Для M4 только исправленные keys-hidden-v3. Для native — только полные серии. Скрипт проверяет совпадение наборов миров, 21 уникальную пару и число моделей. Из корня репозитория: uv run python docs/results/2026-11-26/анализ_пар.py. Зависимости — стандартная библиотека Python и локальный каталог runs.

wilson_* — обычные 95% интервалы отдельных долей в процентах; delta — парная разница долей в процентных пунктах. only_A и only_B показывают, сколько совпадающих миров поменяли исход в каждом направлении. mcnemar_two_sided — точный двусторонний тест по несовпадающим парам. holm_all_exploratory — консервативная поправка Холма по всем 39 строкам как одной описательной семье. Например, в Hermes номинальное p=0,0039, после этой поправки 0,102. Семья выбрана при разборе данных; p здесь разведочные. Значения Wilson и тест предполагают независимость разных пар; три общих шаблона ограничивают перенос результата на новые виды задач.

## Часть 2. Реальные харнесы: фактическая оплата, ответы и повторы

### 1. После потерянного платежа осторожность оставляет работу незавершённой

Назначенный сценарий — первая попытка пропала; задача всё ещё требует оплатить один или несколько счетов. По журналу эффектов проверены **все целевые счета, суммы и отсутствие посторонних списаний**. Справа показан структурированный статус, который вернул родитель. По 84 эпизода в строке, четыре варианта ключа вместе.

| Харнес | Весь заказ оплачен ровно один раз | Остался неоплаченный счёт | Ответ done / unknown / failed | Тот же актор повторно вызвал оплату фокального счёта |
|---|---:|---:|---:|---:|
| Claude Code | 28 | 56 | 27 / 57 / 0 | 28 |
| Hermes | 32 | 52 | 31 / 51 / 2 | 33 |
| Codex | 64 | 20 | 64 / 20 / 0 | 64 |

В этой серии связка Sol + Luna чаще повторяла попытку и чаще завершала оплату. Совпадение итоговых чисел не устанавливает причину для каждого эпизода. Различаются и харнес, и модели.

### 2. Успешное списание не гарантирует правильного отчёта

В обратном сценарии первое списание задумано как выполненное, ответ потерян. На Claude Code все целевые счета правильно оплачены в **76/84**, но родитель вернул unknown в **78/84**. На Hermes — **70/84** и **71/84**, на Codex — **66/84** и **66/84**. Это две отдельные частоты. Поэпизодная проверка сочетания «родитель сказал done, хотя заказ не выполнен ровно один раз» дала **6/84, 10/84 и 18/84** соответственно. Этот критерий относится ко всему заказу.
